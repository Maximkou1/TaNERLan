# TaNERLan — продуктовые материалы (промежуточная версия)

Дата: 2026-09-04. Компактный комплект, обосновывающий продуктовые решения
промежуточного этапа. Источник фактов о бизнес-контексте — материалы кейса
хакатона; техническая часть опирается на эксперименты, описанные в
[PROJECT_STATUS.md](PROJECT_STATUS.md).

## Кто пользователь и какую проблему решает продукт

**Прямой пользователь сервиса** — внутренний конвейер обработки сообщений
Brand Analytics, который автоматически прогоняет через NER-сервис все
собранные узбекоязычные тексты перед агрегацией в отчёты.

**Конечный пользователь ценности** — аналитики, PR-, маркетинговые и
репутационные специалисты клиентов Brand Analytics, которые исследуют
информационное поле Узбекистана через готовые аналитические отчёты. Они не
взаимодействуют с NER-сервисом напрямую и не знают о его существовании —
они видят результат его работы: списки упомянутых организаций, персон и
геообъектов, агрегированные по объёму и динамике упоминаний.

**Проблема, которую решаем**: для русского и английского языков Brand
Analytics уже умеет строить такие отчёты, для узбекского — нет. Клиенты,
которых интересует узбекоязычный рынок, получают заведомо неполную
картину информационного поля и вынуждены закрывать этот пробел вручную
(ручной поиск и разбор упоминаний), что снижает ценность продукта именно в
этом сегменте и ограничивает его развитие на рынке Узбекистана.

## Продуктовая гипотеза и ценностное предложение

**Гипотеза**: если добавить в конвейер Brand Analytics NER-сервис для
узбекского языка с качеством, сопоставимым по методологии измерения с
уже работающими языками (exact-span micro-F1 по классам ORG/NAME/GEO), то
клиенты, отслеживающие узбекоязычный рынок, получат отчёты по
организациям, персонам и геообъектам без ручной доработки — то есть
продукт становится пригоден для полноценного использования в этом
сегменте.

**Ценностное предложение**: автоматическое, воспроизводимое выделение
именованных сущностей в узбекских текстах (латиница, кириллица, смешанные
тексты) с точными символьными границами — как встроенный этап конвейера,
без изменений в том, как клиент потребляет отчёты.

## Границы MVP и основной пользовательский сценарий

**В скоуп MVP входит** (согласно обязательной части кейса):
- выделение сущностей трёх классов — ORG, NAME, GEO — с точными
  символьными границами;
- работа с узбекской латиницей, кириллицей и смешанными
  узбекско-русскими/иноязычными текстами;
- HTTP API, принимающий батч текстов и возвращающий сущности (в формате,
  совместимом с [API.md](API.md));
- готовность к запуску в Docker;
- воспроизводимый пайплайн обучения (фиксированные данные, версия базовой
  модели, конфигурация, seed).

**Явно вне скоупа MVP** (согласно кейсу):
- сбор и разметка нового большого датасета;
- дополнительные типы сущностей сверх ORG/NAME/GEO;
- полноценный пользовательский интерфейс/клиентские отчёты — сервис
  встраивается в существующий конвейер Brand Analytics, отдельного UI не
  создаём;
- промышленная нагрузка, отказоустойчивость, автомасштабирование, SLA.

**Опционально, вне обязательного скоупа, но в рассмотрении команды**:
нормализация сущностей (`Toshkentda` → `Toshkent`), демонстрационный UI
для ручной проверки, замер производительности сервиса.

**Основной пользовательский сценарий** (весь путь до конечного
пользователя):
1. Конвейер Brand Analytics собирает сообщение на узбекском (или смешанном)
   языке из соцсетей/СМИ.
2. Текст отправляется в NER-сервис (`POST /api/v1/predict`).
3. Сервис возвращает список сущностей с типом и точными координатами.
4. Результат агрегируется вместе с сущностями на русском/английском в
   единый отчёт клиента.
5. Аналитик клиента видит в отчёте узбекоязычные упоминания организаций,
   персон и геообъектов наравне с остальными языками и принимает решения
   по коммуникациям/репутации на основе полной картины.

## Предварительные критерии успеха

Формальный порог качества организаторами не задан, поэтому команда
ориентируется на два уровня сравнения:

- **Относительный, промежуточный**: итоговое решение должно
  устойчиво превосходить baseline и zero-shot альтернативы без
  дообучения по exact-span micro-F1 на dev, без критического провала ни
  по одному из трёх классов (ORG/NAME/GEO) — сейчас лучший результат
  (LLM-подход) 0.768 micro-F1, baseline 0.655; продуктовая планка для
  финала — устойчиво выше обеих цифр на закрытой выборке.
- **Технический, обязательный**: решение проходит контрактную проверку
  HTTP API и Docker-контейнера (`scripts/check_service.py`) — без этого
  решение не может быть допущено к оценке качества независимо от F1.

Явный количественный порог (например, "F1 ≥ X") пока не зафиксирован —
это открытый вопрос, см. ниже.

## Ключевые допущения, риски и план проверки до финала

| Допущение / риск | Почему это важно | План проверки до финала |
|---|---|---|
| Одна из уже испытанных архитектур (LLM-подход или дообученный encoder) достаточно хороша для продакшна Brand Analytics | Если нет — нужно менять стратегию задолго до дедлайна, не в последний момент | Свести все подходы по единой методологии (`evaluation.evaluate_model`), выбрать финального кандидата на раннем этапе после результатов ruModernBert |
| LLM-подход (внешний vLLM-сервер, 27B-модель) укладывается в требования по latency/ресурсам финальной проверки (одна A100) | Лучший текущий результат по F1 получен именно этим подходом, но неизвестно, впишется ли он в контейнер с одной A100 | Замерить latency/throughput/VRAM реального инференс-сервиса, сравнить с ориентиром ~5 сек/батч на A100 |
| Инференс-сервер для LLM-подхода стабилен под нагрузкой | На практике уже наблюдали деградацию качества (F1 0.78→0.65) при перегрузке чужой нагрузкой на общем сервере | Если LLM-подход выбран для финала — обеспечить выделенный/контролируемый инференс, а не общий сервер команды |
| Метрика на закрытой тестовой выборке организаторов не сильно разойдётся с dev | Все текущие цифры измерены только на публичном dev; распределение закрытой выборки может отличаться (по FAQ организаторов — не обязано совпадать) | Явно закладывать в отчёт диапазон неопределённости, не заявлять итоговую цифру как гарантированную |
| ModernBERT (после MLM-предобучения и NER-дообучения) даст прирост качества относительно текущего distilbert-baseline | MLM-пайплайн уже реализован (`tanerlan/modern_bert/`), но NER-дообучение и метрики на нём ещё не получены — если прироста не будет, этот трек не попадает в финальное решение, ресурс лучше перераспределить | Довести NER-дообучение до метрик, сравнить по той же методологии (`evaluation.evaluate_model`) до финала |
| Лучшая комбинация train-set аугментаций (транслитерация + внешний корпус, каждая подтвердилась выше noise floor по отдельности) даст суммарный прирост при совместном применении | Пока измерено только по отдельности; аугментации могут не складываться линейно | Собрать оба шага в одном прогоне на baseline, сравнить с суммой отдельных эффектов |

## Связь продуктовых решений с технической реализацией

- Требование **точных символьных границ** (а не приблизительного
  совпадения) напрямую определило инженерное решение LLM-подхода: у
  модели не спрашивают координаты (LLM не умеют считать символы точно),
  а просят поверхностные строки и находят их координаты поиском по
  исходному тексту — иначе строгая метрика гарантированно давала бы
  около нуля.
- Требование **работы с латиницей, кириллицей и смешанными текстами**
  привело к отдельному аудиту (`tanerlan/llm/boundary_audit_train.md`) и
  к явной обработке 6 вариантов написания апострофа в узбекской латинице
  при сопоставлении строк — без этого система систематически теряла бы
  сущности вида `Oʻzbekiston`.
- Требование **воспроизводимого пайплайна** (а не разового результата)
  определило решение вести журнал экспериментов
  (`tanerlan/llm/PROMPT_TUNING.md`) и фиксировать конфигурацию каждого
  прогона, а не полагаться на память/однократный лучший результат.
- Продуктовое ограничение **MVP без отдельного UI** (сервис встраивается
  в существующий конвейер) сняло с промежуточного этапа задачу
  демонстрационного интерфейса — команда сфокусировалась на API и
  качестве, а не на визуализации.

## Открытые продуктовые вопросы к финалу

- Нужна ли нормализация сущностей в границах MVP, или это чисто
  дополнительная задача — зависит от того, насколько клиентам Brand
  Analytics критична агрегация вариантов написания одной сущности
  (`Toshkentda`/`Toshkent`) уже на этом этапе.
- Какой явный количественный порог успеха задать команде самой (раз
  организаторы его не фиксируют) — предлагается закрепить после
  получения результатов ruModernBert.
